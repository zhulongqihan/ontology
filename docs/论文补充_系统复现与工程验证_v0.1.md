# 论文可直接插入内容：系统复现与工程验证

以下内容用于补入论文第六章“系统测试与验证”和第七章“总结与展望”。正文中的数字来自本项目本轮源码、测试报告和运行产物；“实现事实”“实验观察”“推断”“限制”四类表述不可互换。

## 6.X 复现对象、范围与数据身份

**实现事实。** 本文复现对象是 `F:\finalartical\flexible-ontology-reproduction` 中的单机柔性对象引擎及其本体装配、历史接口兼容和管理 API。系统以 `EngineModel`、`SchemaVersionRecord`、`WorkflowVersionRecord`、`RuntimeContextRecord`、`RuntimeRun`、`ExecutionSnapshotRecord`、`TraceRecord`、`AuditEventRecord` 和 `IdempotencyRecord` 表达模型配置、版本、运行上下文、运行结果和证据链。配置和运行数据由 SQLite 规范化表承载，同时保留 JSON compatibility payload；运行时结果使用 `ENGINE_RUNTIME_RESULT`，独立契约实验使用 `ENGINE_EXPERIMENT_RESULT`。

**实验观察。** 当前仓库内的 `data/flexible-engine.db` 和 `data/engine-state.json` 是历史运行产物，未被 Git 跟踪。只读状态审计观察到历史 SQLite schema version 为 4，而当前 loader 的目标版本为 14；数据库中存在缺少当前 Trace/Snapshot/版本身份的历史运行记录，服务注册中仍可能出现旧的 `OntologyAssembler` 名称。上述数据没有被删除，也没有为其补造 Trace；重新加载时将其标记为 `LEGACY_RUNTIME_RECORD`。因此，历史产物可以作为兼容边界的证据，不能作为当前运行的完整证据。

**限制。** 本文的“复现”指基于现有代码、需求、架构决策和契约材料构建的本地工程行为复现，不等同于原生产系统的黑盒一致性验证。当前 Provider 的 Trace 属性为 `transport=IN_PROCESS`，实现类为 `LocalOntologyProvider`；本文不据此声称完成远程 Provider、跨服务 RPC、生产部署、HA、性能容量或业务收益复现。新增的 D 组实验只使用仓库内独立实现的 `RigidMappingBaseline v1` 作为工程对照。

## 6.X 领域边界与运行证据链

系统将配置写入和运行提交分为两条边界。配置命令通过 `EngineAdminService` 修改 `EngineModel`、本体类型或服务注册，追加带 `beforeRevision`、`afterRevision` 和 structured changes 的 audit event。运行命令由 `EngineRuntimeService.execute` 执行，读取当前 Schema/Workflow，迁移落后的 Context，生成 Before/After Snapshot 和 Trace；只有运行成功时才推进 Context 的 state、values、revision 和 last run 信息，失败运行只追加 Run 记录而不推进成功上下文。

运行提交的核心逻辑可概括为以下伪代码：

```text
读取 model、context、event、values、ontology
计算 request_sha256(model, context, event, values, ontology)
若幂等键已存在且 hash 相同：返回原 Run
若幂等键已存在但 hash 不同：拒绝请求
按相邻 Schema 版本迁移 Context；失败则不改变 Context
校验字段和事件，按配置装配 ontology graph 和 Local Provider
生成 BEFORE/AFTER Snapshot、Trace、Run
若全部阶段成功：推进 Context revision；否则保持原 Context
在 revision 条件下写入 SQLite/JSON 兼容状态
```

**实现事实。** 本轮补充了两项容易被页面掩盖的边界：第一，幂等指纹包含 ontology 输入，而不是只包含 model、context、event 和 values；第二，运行入口对嵌套 Map/List 做深拷贝，避免调用者在返回后修改原始对象而污染 Run 或 Snapshot。`VersionedSchema` 同时拒绝跳跃发布版本；`OntologyGraphValidator` 对精确 `1:1` 关系在零条目标边时也拒绝。

## 6.X 坏数据、恢复和不可声称内容

投影加载采用“先校验、后加载、再同步”的顺序。坏当前 Schema、字段版本、Trace identity、审计 changes JSON 和备份数据库均由测试证明会被拒绝；恢复流程在临时库中完成迁移和完整性校验后才替换 live database。对于历史运行记录，系统只允许具有明确历史形状的记录进入兼容边界：其 engine/schema/workflow 证据缺失或 Trace/Snapshot 不完整时标为 `LEGACY_RUNTIME_RECORD`，不得将其计入当前运行成功率或当前 Trace 覆盖率。

由此得到的工程结论是：数据库“能打开”与“当前运行证据完整”是两个不同命题。前者由 legacy 兼容规则支持，后者必须要求当前版本身份、Run、Trace 和 Snapshot 彼此匹配。本文不把兼容加载推断为历史业务行为已经重现。

## 6.X 固定基线与 Flexible Engine 的成对实验

**实现事实。** 为避免把两次同引擎运行误写成“使用柔性引擎前后”，系统增加独立的 `RigidMappingBaseline`。该基线只按预先声明的固定字段和固定状态转移执行，不调用 `FlexibleEngine`、本体配置或 Provider；`EngineRuntimeService.executeComparison` 为同一输入创建 baseline Run 和 Flexible Engine Run，并写入相同的 `input_sha256`、不同的 `configuration_sha256`、`comparisonId` 和互相指向的 `pairedRunId`。

**实验协议。** D 组包含三个案例：基础问卷、增加 `reviewerNote` 动态字段的问卷、带 `subjects/options` 运行时图谱的问卷。每个案例执行 12 次，每次使用独立临时 SQLite，从相同默认种子开始，先运行固定基线再运行 Flexible Engine。最终结果文件为 `docs/实验证据/20260903_evolution_capability_final/D/result.json`、逐案例 observations JSON 和 `duration-comparison.svg`。耗时记录为 `duration_ns`，以避免子毫秒运行被取整为零；p50/p95 是本机本地实现的原始观测。

| 案例 | 可比较配对 | 基线通过 | Flexible Engine 通过 | 基线失败而柔性通过 | baseline p50/ns | flexible p50/ns | p50 差值/ns |
|---|---:|---:|---:|---:|---:|---:|---:|
| questionnaire-basic | 12/12 | 12/12 | 12/12 | 0/12 | 418,700 | 1,286,100 | 867,400 |
| questionnaire-dynamic-field | 12/12 | 0/12 | 12/12 | 12/12 | 428,600 | 1,105,800 | 666,400 |
| questionnaire-knowledge-graph | 12/12 | 12/12 | 12/12 | 0/12 | 446,500 | 1,271,300 | 898,100 |

**实验观察。** 动态字段案例中，固定基线在 12 次试验全部因未声明 `reviewerNote` 失败，而 Flexible Engine 在 12 次试验全部通过；三个案例的输入哈希均稳定，baseline/flexible 配置哈希均在重复试验内稳定且彼此不同。该结果支持“在该案例和该固定基线下，柔性配置能够承接新增字段”的工程观察，不支持原生产系统兼容率、性能提升或业务收益结论。基础和图谱案例中柔性侧 p50 耗时更高，说明柔性机制的可配置性存在本地执行开销，论文不应把所有指标都写成提升。

**可复核步骤。** 先执行 `mvn.cmd clean package`，再执行 `java.exe "-Dreproduction.source.revision=$(git rev-parse HEAD)" -jar reproduction-app\target\reproduction-app-0.1.0-SNAPSHOT.jar experiments experiments\contract-20\contract-20.csv <output>`，最后检查 D 组 `result.json` 的 `input_hashes_consistent`、`baseline_configuration_hash_consistent` 和 `flexible_configuration_hash_consistent`。`comparisonId`、Run、Trace、Snapshot 和 SQLite 投影均可从程序重新生成；历史数据库不参与该实验。

## 6.X E 阶段：Schema 演化能力矩阵

**实现事实。** E 阶段由 `ReproductionExperimentSuite.evolutionCapabilityMatrix` 调用真实的 `EngineAdminService`、`EngineRuntimeService.executeComparison` 和 `SqliteEngineStateRepository`。每个案例先在新的默认种子上执行 Schema 配置操作，再用同一输入分别运行 `RigidMappingBaseline` 与 Flexible Engine。每一对 Run 都保存 `comparisonId`、互指的 `pairedRunId`、输入/配置 hash、Before/After Snapshot、Trace 生命周期和耗时。`completeEvidence` 只有在这些字段存在、Trace 已封存且为 `COMMITTED`、Run/Trace 身份匹配、Span 数量不少于 4 时才返回真。

**实验观察。** 最终产物 `docs/实验证据/20260903_evolution_capability_final/E/result.json` 显示：36/36 对输入可比，固定映射基线通过 12/36，Flexible Engine 通过 36/36；其中 24/36 对满足“baseline 失败且 flexible 通过”，适应性增益率为 `24/36=66.67\%`，36/36 对的证据门禁完整，所有案例的输入 hash 在 12 次重复中保持一致。三个案例分别为：新增 `panelId` 字段（0/12→12/12，12 对提升）；`candidateName` 到 `applicantName` 的显式重命名（schema v3、12/12 次记录 1 条迁移，0/12→12/12，12 对提升）；新增 `subjects(JSON)` 并输入 subject/options（12/12→12/12，无结果提升但保留运行图谱证据）。

| 案例 | 可比较配对 | 基线通过 | Flexible Engine 通过 | 基线失败而柔性通过 | Schema 迁移观测 | 证据完整 |
|---|---:|---:|---:|---:|---:|---:|
| 面试新增字段 | 12/12 | 0/12 | 12/12 | 12/12 | 0 | 12/12 \\
| 面试字段重命名 | 12/12 | 0/12 | 12/12 | 12/12 | 12 | 12/12 \\
| 动态关系图谱 | 12/12 | 12/12 | 12/12 | 0/12 | 0 | 12/12 \\

**解释边界。** E 的 66.67\% 是当前仓库固定映射基线、三个预先定义案例和 12 次重复条件下的适应性差异，不是原生产系统兼容率、通用柔性提升、统计显著性或业务收益。字段重命名案例证明当前实现确实消费了迁移后的 Schema，而不是只修改了展示文案；图谱案例的结果不应被计入“成功率提升”，因为两侧均通过。

## 7.X 对原有历史统计的校正

原稿中出现的“37 条局部断言全部通过”和 `InterviewSessionJsfServiceImplTest` 的“59 条中 51 条通过、1 条失败、7 条错误（86.44%）”属于历史材料统计。它们可以保留为历史背景或原系统线索，但不能替代当前工程的 Maven 结果，也不能被表述为本项目本轮复现率。本轮工程测试规模为 91 条自动化测试；契约实验规模为每个 seed 20 条、3 个 seed 共 60 条；D 组为三个案例各 12 次固定基线成对试验，E 组为三个演化案例各 12 次固定基线成对试验，并且各组的统计口径、输入数据和 data identity 不同。

## 7.X 研究结论与有效性威胁

本轮证据支持的结论是：在固定源码和本地 fixture 条件下，柔性模型、版本迁移、运行上下文、失败不提交、幂等、回滚、本体装配、Provider 错误、SQLite 投影、契约适配和 Schema 演化对照能够形成可重复的单机工程链路。E 阶段的新增字段与字段重命名案例观察到 24/36 对适应性增益，但该结果仍然属于仓库内固定基线下的工程观察。该结论来自当前代码、JUnit 断言和运行产物的交叉证据，而不是来自页面截图。

有效性威胁包括：第一，契约用例基于重构后的行为规格，`spec_basis=RECONSTRUCTED_BEHAVIOR`，缺少原系统同版本黑盒结果；第二，Provider 是进程内本地实现，Trace 不代表跨服务网络调用；第三，运行产物未全部进入 Git，其他环境需要根据 manifest、固定 seed 和命令重新生成；第四，当前本体基数校验已覆盖 source/target 两端的计数边界，但尚未覆盖并发关系写入和大规模图谱性能；第五，Model--Ontology 显式绑定已经持久化并执行版本/hash 校验，但尚未覆盖跨部署版本迁移样本；第六，persistence 和 response span 在实际保存/响应完成前加入 Trace，因而只能证明阶段准备和执行路径，不能证明外部交付完成。

因此，本文将系统定位为“具备可复核状态、证据和兼容边界的单机工程复现”，不将其提升为原生产系统复现、通用本体平台、分布式事务系统或生产性能结论。
