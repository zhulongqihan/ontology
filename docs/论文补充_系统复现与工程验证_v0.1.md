# 论文可直接插入内容：系统复现与工程验证

以下内容用于补入论文第六章“系统测试与验证”和第七章“总结与展望”。正文中的数字来自本项目本轮源码、测试报告和运行产物；“实现事实”“实验观察”“推断”“限制”四类表述不可互换。

## 6.X 复现对象、范围与数据身份

**实现事实。** 本文复现对象是 `F:\finalartical\flexible-ontology-reproduction` 中的单机柔性对象引擎及其本体装配、历史接口兼容和管理 API。系统以 `EngineModel`、`SchemaVersionRecord`、`WorkflowVersionRecord`、`RuntimeContextRecord`、`RuntimeRun`、`ExecutionSnapshotRecord`、`TraceRecord`、`AuditEventRecord` 和 `IdempotencyRecord` 表达模型配置、版本、运行上下文、运行结果和证据链。配置和运行数据由 SQLite 规范化表承载，同时保留 JSON compatibility payload；运行时结果使用 `ENGINE_RUNTIME_RESULT`，独立契约实验使用 `ENGINE_EXPERIMENT_RESULT`。

**实验观察。** 当前仓库内的 `data/flexible-engine.db` 和 `data/engine-state.json` 是历史运行产物，未被 Git 跟踪。只读状态审计观察到历史 SQLite schema version 为 4，而当前 loader 的目标版本为 12；数据库中存在缺少当前 Trace/Snapshot/版本身份的历史运行记录，服务注册中仍可能出现旧的 `OntologyAssembler` 名称。上述数据没有被删除，也没有为其补造 Trace；重新加载时将其标记为 `LEGACY_RUNTIME_RECORD`。因此，历史产物可以作为兼容边界的证据，不能作为当前运行的完整证据。

**限制。** 本文的“复现”指基于现有代码、需求、架构决策和契约材料构建的本地工程行为复现，不等同于原生产系统的黑盒一致性验证。当前 Provider 的 Trace 属性为 `transport=IN_PROCESS`，实现类为 `LocalOntologyProvider`；本文不据此声称完成远程 Provider、跨服务 RPC、生产部署、HA、性能容量或业务收益复现。

## 6.X 领域边界与运行证据链

系统将配置写入和运行提交分为两条边界。配置命令通过 `EngineAdminService` 修改 `EngineModel`、本体类型或服务注册，追加带 `beforeRevision`、`afterRevision` 和 structured changes 的 audit event。运行命令由 `EngineRuntimeService.execute` 执行，读取当前 Schema/Workflow，迁移落后的 Context，生成 Before/After Snapshot 和 Trace；只有运行成功时才推进 Context 的 state、values、revision 和 last run 信息，失败运行只追加 Run 记录而不推进成功上下文。

运行提交的核心逻辑可概括为以下伪代码：

```text
读取 model、context、event、values、ontology
计算 request_sha256(model, context, event, values, ontology)
若幂等键已存在且 hash 相同：返回原 Run
若幂等键已存在但 hash 不同：拒绝请求
按相邻 Schema 版本迁移 Context；失败则不改变 Context
校验字段和事件，按配置装配 ontology graph 和 Local Provider
生成 BEFORE/AFTER Snapshot、Trace、Run
若全部阶段成功：推进 Context revision；否则保持原 Context
在 revision 条件下写入 SQLite/JSON 兼容状态
```

**实现事实。** 本轮补充了两项容易被页面掩盖的边界：第一，幂等指纹包含 ontology 输入，而不是只包含 model、context、event 和 values；第二，运行入口对嵌套 Map/List 做深拷贝，避免调用者在返回后修改原始对象而污染 Run 或 Snapshot。`VersionedSchema` 同时拒绝跳跃发布版本；`OntologyGraphValidator` 对精确 `1:1` 关系在零条目标边时也拒绝。

## 6.X 坏数据、恢复和不可声称内容

投影加载采用“先校验、后加载、再同步”的顺序。坏当前 Schema、字段版本、Trace identity、审计 changes JSON 和备份数据库均由测试证明会被拒绝；恢复流程在临时库中完成迁移和完整性校验后才替换 live database。对于历史运行记录，系统只允许具有明确历史形状的记录进入兼容边界：其 engine/schema/workflow 证据缺失或 Trace/Snapshot 不完整时标为 `LEGACY_RUNTIME_RECORD`，不得将其计入当前运行成功率或当前 Trace 覆盖率。

由此得到的工程结论是：数据库“能打开”与“当前运行证据完整”是两个不同命题。前者由 legacy 兼容规则支持，后者必须要求当前版本身份、Run、Trace 和 Snapshot 彼此匹配。本文不把兼容加载推断为历史业务行为已经重现。

## 7.X 研究结论与有效性威胁

本轮证据支持的结论是：在固定源码和本地 fixture 条件下，柔性模型、版本迁移、运行上下文、失败不提交、幂等、回滚、本体装配、Provider 错误、SQLite 投影和契约适配能够形成可重复的单机工程链路。该结论来自当前代码、JUnit 断言和运行产物的交叉证据，而不是来自页面截图。

有效性威胁包括：第一，契约用例基于重构后的行为规格，`spec_basis=RECONSTRUCTED_BEHAVIOR`，缺少原系统同版本黑盒结果；第二，Provider 是进程内本地实现，Trace 不代表跨服务网络调用；第三，运行产物未全部进入 Git，其他环境需要根据 manifest、固定 seed 和命令重新生成；第四，`OntologyCardinality` 当前主要约束每个 source 的 target count，source multiplicity 的反向约束尚未实现；第五，`EngineModel` 尚无显式 `ontologyTypeId`，当前绑定依赖 model id 与 ontology type id/label 的同名规则；第六，persistence 和 response span 在实际保存/响应完成前加入 Trace，因而只能证明阶段准备和执行路径，不能证明外部交付完成。

因此，本文将系统定位为“具备可复核状态、证据和兼容边界的单机工程复现”，不将其提升为原生产系统复现、通用本体平台、分布式事务系统或生产性能结论。
