# ADR-004：运行证据与事务边界

日期：2026-09-02
状态：Accepted

## 背景

运行结果不能只保留状态迁移后的字段。论文级复核需要知道运行前状态、运行后状态、使用的 Schema/Workflow 版本、Trace 阶段和失败是否提交上下文。原实现以最近一条 Run 推断上下文，无法区分失败尝试与成功提交，也无法处理重复请求。

## 决策

1. `RuntimeContextRecord` 是当前上下文的唯一可变事实；只有运行成功时才更新业务状态、字段和 revision。
2. `RuntimeRun` 创建后只追加，不提供更新接口；它固定记录 `engineVersion`、`schemaVersion`、`workflowVersion`、`contextRevision`、幂等键、before/after Snapshot 和错误码。
3. Snapshot 使用核心 `ExecutionSnapshot` 计算规范化 SHA-256；Trace 必须包含 `runId` 和请求、校验、工作流、本体、Provider、持久化、响应 Span，并在写入前封存。Provider Span 必须区分真实调用、跳过和失败。
4. 同一模型和上下文作用域内，幂等键绑定一个请求哈希和一个 Run。相同请求返回原 Run，不同请求使用同键时拒绝。
5. JSON 是兼容迁移和备份格式；SQLite 的配置域与运行域规范化表在同一事务中作为可查询投影写入。投影缺失的旧运行保留在历史 JSON 状态中，但不回填为新证据。
6. 每次状态写入使用 `EngineState.revision` 做乐观锁；旧写入方收到 revision conflict，HTTP 层转换为 409。
7. 失败 Run 只能追加生成新的 retry attempt，不修改原 Run；成功 Run 只能在其仍是上下文最新提交时回滚，回滚本身也作为新的 `ROLLED_BACK` Run 和 `RUN_ROLLED_BACK` 审计事件持久化。
8. 配置域在 SQLite 中拆分为模型、Schema、Workflow、本体和服务表，并与状态文档在同一写事务中更新；读取优先从规范化表重建，状态文档退为运行历史兼容备份，配置投影不反向覆盖状态。

## 后果

- 失败运行可以被审阅，但不能污染上下文。
- 重启后可以通过 Run、Snapshot、Trace、Context 和幂等记录重建运行事实。
- 当前仍保留状态文档兼容层；配置和运行事实已从规范化表直读重建，旧 JSON 仅在旧库缺少投影时回退，加载前会拒绝断链、外键不一致或损坏审计差异的投影；配置写入已记录字段级 before/after，后续仍需多实例并发审计。
- 重试和回滚已经具备可追踪的运行事实，但故障注入和策略化重试仍属于后续能力。
- 本地 Provider 已纳入 Trace 证据边界；契约实验中的 Trace 时间和耗时来自真实调用，因此每次运行的 Trace 哈希允许变化，只有不含运行时钟的报告哈希用于判断契约结果是否稳定。
- 配置可以按领域表独立查询和检查；在完成投影校验前，运行域查询保留规范化表缺失时的状态聚合兼容回退，避免旧库升级时丢失历史。
