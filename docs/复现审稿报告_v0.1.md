## 1. 结论先行

### 1.1 复现等级与可信度

当前复现等级：**工程可运行**。
复现可信度：**中**。

这里的“工程可运行”只表示：在当前源码和临时隔离状态库上，动态模型、Schema/Workflow 版本、运行上下文、失败/重试/回滚、Trace、Provider 边界、SQLite 恢复和 20 条契约实验可以被执行并由自动化测试复核；它不表示已经复现原生产系统，也不表示具备远程服务、HA、容量、业务收益或生产数据证据。

可信度没有评为“高”的原因有三点：

1. `data/flexible-engine.db` 是历史运行产物而不是 Git 跟踪的可审计 fixture；初始打开时只有 SQLite schema v4，且有 3 条缺失当前证据链的运行记录。旧代码会把其中的运行行当作当前运行并因 Trace 不匹配启动失败。本轮已改为保留并显式标记 legacy，但历史记录本身没有被补造为当前证据。
2. 论文原稿仍主要叙述历史代码和历史测试，原稿中的 37 条局部断言及 `InterviewSessionJsfServiceImplTest` 的 59 条统计不能替代当前平台 74 条自动化测试、SQLite 重启和契约实验的证据。
3. 当前实现是单机、进程内 `LocalOntologyProvider`，没有远程 Provider、跨服务 RPC、权限体系、HA、性能基线和与原系统同版本的黑盒对照。因此可以声称“本地工程行为被复现”，不能声称“生产系统行为或业务结果被复现”。

### 1.2 最严重的三个问题

| 问题 | 现象 | 根因 | 本轮处理 | 当前影响 |
|---|---|---|---|---|
| 历史 SQLite 打不开 | 初始 admin 启动在 `validateNormalizedProjection` 因 `runtime_run` 指向缺失 Trace 失败 | 旧运行记录已被改写成当前 `ENGINE_RUNTIME_RESULT`，投影校验没有历史记录边界 | 保留历史记录、显式使用 `LEGACY_RUNTIME_RECORD`；当前版本仍拒绝“有完整版本身份但缺 Trace”的新运行 | 旧数据可启动，但 legacy 运行不能作为当前运行证据 |

### 1.3 最容易被审稿人质疑的三个点

1. **“复现”的对象不清楚。** 当前代码是目标架构的本地工程重构，契约实验的 `spec_basis` 是 `RECONSTRUCTED_BEHAVIOR`，不是原系统黑盒复验；原稿若写成“原系统已复现”，证据不足。
2. **本体绑定不是显式模型关系。** `EngineRuntimeService.ontologyTypeIdOrUnknown` 以 `modelId` 与本体 `id/label` 同名作为绑定条件，`EngineModel` 没有 `ontologyTypeId` 字段；注册新模型和注册新本体都能持久化，但两者不能通过独立绑定命令建立明确关系。
3. **Trace 中 persistence/response span 的语义强度不足。** 两个 span 在 `repository.save` 和响应序列化之前就被加入，能够证明执行路径准备过这两个阶段，不能严格证明外部持久化提交或 HTTP 响应已经完成；代码当前未把保存失败建模为已封存的 FAILED Trace。

## 3. 分层架构审查

### 3.1 领域模型与聚合边界

已实现并通过测试的边界是：`EngineState` 作为本地管理状态容器；`EngineModel` 内含当前字段、Schema 历史、Workflow 历史和迁移规则；`RuntimeContextRecord` 保存可继续执行的上下文；`RuntimeRun` 保存一次不可重复覆盖的运行证据；`OntologyTypeConfig` 和 `ServiceRegistration` 属于注册配置。管理命令经 `EngineAdminService` 产生 audit event、revision 和持久化。

证据：`EngineAdminServiceTest.configurationChangesProduceAuditEventsAndStaleWritersAreRejected`、`auditEventsCarryTheStateRevisionTheyBelongTo`、`ontologyAndProviderChangesUseAuditedCommands`、`repeatingAnIdenticalConfigurationCommandIsIdempotent`。

边界不足：`EngineModel` 没有显式 ontology binding；运行服务通过 model id 与 ontology type 同名推断根类型。因而“模型、本体、服务均可注册”已证明，“任意模型可配置绑定任意本体”未实现。

### 3.2 Schema/Workflow 版本与迁移

`EngineAdminService` 的字段新增、rename、remove 会发布新 Schema 版本，Workflow 版本也有历史记录；`EngineRuntimeService.migrateContextValues` 在上下文版本落后时按相邻版本迁移，并在失败时不提交上下文。`VersionedSchema` 也已补充连续版本门禁。

证据：`runtimeMigratesAStaleContextToTheCurrentSchemaBeforeValidation`、`failedSchemaMigrationDoesNotAdvanceTheContext`、`runtimeAppliesAnExplicitRenamedFieldMigrationAcrossVersions`、`VersionedSchema` 的 `versionedSchemaRejectsGapsInPublishedHistory`。

限制：没有通用 Replay 命令；只有继续执行旧 Context 的迁移，不等于可以按旧 Trace 无副作用地回放全部外部调用。

### 3.3 RuntimeContext、Run、Snapshot、Trace、Audit、幂等

实现有明确成功提交边界：只有运行成功时 Context revision/state/value 才推进；失败 Run 留在历史中但不污染 Context。Run 有 `contextRevision`、`contextCommitted`、`attempt`、`retryOfRunId`、`idempotencyKey`、Before/After Snapshot 和 sealed Trace。幂等 hash 现在包含 model、context、event、values 与 ontology 输入；重复请求返回原 Run，语义不同请求复用同 key 会拒绝。

证据：`runtimeContinuesFromThePreviousSnapshotWhenContextIsReused`、`failedRunDoesNotChangeThePersistedContext`、`failedRunCanBeRetriedAsANewAttempt`、`passedRunCanBeRolledBackOnlyAtTheLatestContextRevision`、`idempotentRequestReturnsTheOriginalRunWithoutAdvancingAgain`、本轮新增 `idempotencyBindsOntologyInputAsPartOfTheRequest` 和 `runtimeCopiesNestedCallerValuesBeforePersistingEvidence`。

需要保守解释的是 Trace 的后半段：persistence/response span 在保存和响应完成前记录，不能作为“已提交/已发送”的强证明；这是 P1 限制，不应在论文中夸大为完整分布式 tracing。

### 3.4 本体关系与 Provider/Consumer 边界

`OntologyGraphValidator` 检查对象 id 唯一、类型存在、固定属性、动态属性、目标类型、重复边和每个源对象的目标数量；本轮补上了精确 `1:1` 关系在“零条边”时的拒绝。`LocalOntologyProvider` 组装 Questionnaire/Subject/Option 图并执行验证。运行服务拒绝不存在、DOWN 或未绑定的 Provider，不把未知实现静默回退到本地实现。

证据：`questionnaireRuntimeCanEmitAnObjectGraph`、`unavailableOntologyProviderIsCapturedAndDoesNotCommitContext`、`unboundProviderImplementationIsRejectedInsteadOfSilentlyFallingBack`、`ontologyRuntimeRejectsConfiguredTargetTypeMismatch`、`ontologyRuntimeRejectsOneToOneCardinalityOverflow`、本轮新增 `rejectsMissingTargetForExactOneToOneRelation`。

明确边界：当前 Provider 是进程内本地实现；`OntologyCardinality` 的 source multiplicity 被解析保存但只对右侧 target count 作约束，反向多源约束尚未实现。

### 3.5 Service/API/HTTP 错误、并发和协议

`EngineAdminServer` 为错误返回 `errorCode`、`message`、`traceId`，支持 `ETag`/`If-Match` revision 冲突，CORS 已声明 `If-Match` 并暴露 `ETag`/`X-Trace-Id`。`EngineAdminService` 在单进程内同步，SQLite 写入再以 revision 检查拒绝 stale writer。

证据：`httpConfigurationUpdatesAndErrorsHaveStableContracts`、`corsPreflightAdvertisesConditionalWriteAndEvidenceHeaders`、`configurationChangesProduceAuditEventsAndStaleWritersAreRejected`。

未实现：前端目前没有对所有写请求自动携带并重试 `If-Match`；服务也不是远程分布式一致性协议。论文应称“单节点乐观版本冲突门禁”，不能称“分布式并发控制”。

### 3.6 JSON/SQLite 投影、事务、迁移、恢复和坏数据拒绝

SQLite 当前 loader 期望 schema v8，迁移脚本为 `engine-persistence/src/main/resources/migrations/001` 至 `008`；配置、运行上下文、Run、Snapshot、Trace、span、audit、幂等均有规范化表，同时保留 JSON payload。打开数据库时先验证投影，再从规范化表加载，最后同步投影；备份恢复采用临时库验证后原子替换。

证据：`persistsEngineStateAcrossRepositoryReloads`、`runtimeDomainProjectionSurvivesRepositoryRestart`、`restoresOnlyAValidatedBackupAndLeavesLiveDatabaseUntouchedOnFailure`、`rejectsBrokenNormalizedProjectionBeforeRewritingCompatibilityPayload`、`rejectsRuntimeRunWithMismatchedTraceIdentity`、`rejectsMalformedAuditChangeSetBeforeRewritingCompatibilityPayload`、本轮新增 `retainsEvidenceIncompleteRuntimeRowsAsExplicitLegacyRecords`。

修复后的恢复规则是：有完整当前版本身份但缺 Trace 的运行行仍拒绝；缺少 engine/schema/workflow 证据或缺失 Trace/Snapshot 的历史形状允许载入，但被 `LEGACY_RUNTIME_RECORD` 标记，不能支撑当前运行声明。该规则是兼容边界，不是证据补全。

### 3.7 前端真实消费

前端 `App.tsx` 从 `/api/overview`、`/api/models`、`/api/ontology/types`、`/api/services`、`/api/runs`、`/api/audit-events`、`/api/idempotency-records` 和运行详情接口读取服务状态；本轮修复 Trace span 的字段名从错误的 `id` 对齐后端的 `spanId`，并在审计面板展示 revision 和 change count。此前页面即使能显示，也不能证明数据模型正确消费。

证据：`frontend/src/api.ts`、`frontend/src/App.tsx`、`EngineAdminServerTest.httpExecuteReturnsQueryableRunSnapshotsAndTrace`；生产构建需以本轮 `npm.cmd run build` 结果为准。

### 3.8 实验链路与引擎运行状态隔离

`ContractExperimentRunner` 建立独立的内存问卷 Provider、固定 seed、每用例 request/response/trace/result/hash 和 manifest；报告 identity 为 `ENGINE_EXPERIMENT_RESULT`，与 engine runtime 的 `ENGINE_RUNTIME_RESULT` 分开。兼容 case 现在把 CSV 的旧字段名真实送入 `JsfExAssessService` 的 request-boundary 方法。

证据：`ContractExperimentRunnerTest.executesAllTwentyContractSpecifications`、`writesPerCaseRequestResponseAndTraceArtifacts`、输出目录中的 `manifest.json`、`C-03/request.json`。

限制：实验数据是确定性内存 fixture，不是生产数据；实验报告不能证明业务收益、真实 Provider 延迟或原系统一致率。

## 5. 严重度问题清单

### P0：会导致复现结论失效

#### P0-1 历史 SQLite 与当前证据协议不兼容（已修复代码根因，历史数据仍为 legacy）

- 现象：对原 `data/flexible-engine.db` 的真实 admin 启动曾失败，异常链为 `cannot load SQLite engine state` → `runtime_run points to a mismatched trace: run-b53adf33`。
- 根因：历史运行行缺 Trace/Snapshot/版本身份，但在之前迁移中被改成 `ENGINE_RUNTIME_RESULT`；校验没有区分历史形状和当前形状。
- 影响：重启恢复结论失效，且若直接删除旧行或补造证据会污染事实。
- 证据：`SqliteEngineStateRepository.validateNormalizedProjection`、原始数据库中 `runtime_run`/`trace`/`execution_snapshot` 计数、修复前 admin smoke 输出。
- 修复：保留历史行；缺完整版本身份或 Trace/Snapshot 的历史行在加载后标记 `LEGACY_RUNTIME_RECORD`；有完整当前身份但缺 Trace 继续拒绝。
- 验证：`retainsEvidenceIncompleteRuntimeRowsAsExplicitLegacyRecords`；临时复制原数据库后 admin 真实启动成功，health `UP`，3 条 legacy 运行被保留。

#### P0-2 不能把当前运行证据与实验报告混为一谈

- 现象：旧契约产物 identity 为 `REPRODUCED_SYSTEM_RUN`，而当前代码定义是 `ENGINE_EXPERIMENT_RESULT`。
- 根因：运行产物未随实验 runner 版本同步；实验和 engine runtime 的身份边界曾不稳定。
- 影响：20/20 即使通过，也无法知道它是引擎运行还是契约实验。
- 修复：runner 固定 `ENGINE_EXPERIMENT_RESULT`，manifest 记录 source revision；脚本检查 data identity。
- 验证：`ContractExperimentRunnerTest.executesAllTwentyContractSpecifications`、新生成报告和 manifest。

### P1：会导致论文主张不可靠

#### P1-1 模型—本体绑定是隐式同名约定

- 现象：新注册模型 id 为 `assessment-session` 时，即使存在另一个本体类型，runtime 仍会得到 `ontology type not found: assessment-session`。
- 根因：`EngineModel` 没有 binding 字段；`ontologyTypeIdOrUnknown` 只按 model id/label 查找。
- 影响：需求中“模型配置本体关系”的强主张不成立；当前只能证明 seed 中同名 Questionnaire 模型能运行。
- 修复方案：增加显式 `ontologyTypeId`、绑定命令、版本化绑定和 SQLite schema migration；本轮未擅自扩大 schema，因为会改变已有数据契约。
- 验证方式：新增跨 id binding 测试、SQLite migration 测试、重启测试后再提升状态。

#### P1-2 persistence/response Trace span 的确认语义过强

- 现象：`EngineRuntimeService.execute` 在调用 `repository.save` 前就加入 persistence `OK`，在返回前就加入 response `OK`。
- 根因：当前 Trace 是内存中组装后随 Run 一起保存，无法在保存失败后把同一 Run 的保存结果追加进去。
- 影响：Trace 可以复核阶段顺序和 Provider 请求，但不能证明保存提交或响应交付。
- 修复方案：将 persistence span 改为 save 前 `STARTED`、save 成功后由新的提交证据封存；响应 span 改为 server write completion 或明确标记 `PREPARED`。本轮保留现状并在论文降级表述。
- 验证方式：注入 save failure、检查失败 Run/Trace 语义，以及 HTTP 客户端收到响应后的端到端记录。

#### P1-3 当前论文原稿与当前工程证据错位

- 现象：原稿 Chapter 6 主要报告历史 37/37 与 51/59，契约 20 条仍写作“设计”，没有当前 SQLite/Trace/audit 实现。
- 根因：论文没有绑定 source revision、实验 manifest 和本轮 Maven 结果。
- 影响：审稿人无法从论文复核当前系统，也会误把历史失败率当当前工程质量。
- 修复：新增 [`docs/论文补充_系统复现与工程验证_v0.1.md`](./论文补充_系统复现与工程验证_v0.1.md)，并在外部 `正文.tex` 增加当前系统验证、数据身份和限制章节。
- 验证方式：论文正文逐项对应本报告矩阵；所有数字标记为实现事实或实验观察。

#### P1-4 契约实验旧字段曾未真正进入适配层（已修复）

- 现象：C-03/C-07/C-11/C-15/C-19 的 scenario 是 compatibility，但原 runner 用规范参数生成请求。
- 根因：runner 依据 scenario 选择输入，而非解析 CSV 的 `request_shape`。
- 影响：兼容率虚高，测试只测了 provider 正常路径。
- 修复：CSV shape parser + `JsfExAssessService` 显式 request-boundary alias methods。
- 验证：C-03 request artifact 含 `legacy_subject_id`；兼容 adapter 新测试和 20-case runner 测试通过。

#### P1-5 当前产物未被 Git 跟踪

- 现象：`git ls-files data` 和 `git ls-files runs` 不返回当前 DB/JSON/实验输出。
- 根因：运行产物被 `.gitignore` 忽略，缺少 manifest 与版本绑定策略。
- 影响：其他机器不能只靠提交 hash 得到同一数据库和报告；论文的数字难以审计。
- 修复：新增只读状态审计脚本、runner source revision；不把历史 DB 强行加入 Git。
- 验证方式：提交后用干净 checkout、固定 seed、临时状态库和实验命令重新生成，并保存 manifest/hash；若需要长期 artifact，应另设版本化 fixture 或制品仓库。

### P2：影响工程质量但不破坏核心结论

- `VersionedSchema` 是低层 utility，admin 另有版本模型；本轮补了连续版本门禁，但两套版本抽象仍可能造成维护歧义。
- `OntologyCardinality` 解析了 source multiplicity 但只实施 target count；须在论文明确“本实现只验证每个 source 的 target 数量”。
- 前端目前不自动读取 ETag 并在写请求中发送 If-Match；服务端协议已具备，前端闭环未完成。
- legacy Provider 名称的启动归一化属于兼容迁移，不是用户可审计配置命令；应在审计解释中单独标记。
- 默认 `ReproductionApplication` smoke 是核心流程/兼容详情示例，不等于 admin SQLite smoke；两者应分别列出。

### P3：表达、结构或体验问题

- 原稿章节仍将“契约验证设计”和“契约实测结果”混在一起，需要拆开。
- 原稿应将“历史原系统线索”“当前重构实现”“本轮实验观察”用不同小节和标签表示。
- 前端证据页应显示 legacy 运行的证据状态，避免用户看到一行运行记录就默认它有完整 Trace/Snapshot。
- 产物路径、source revision、seed、data identity 应在论文表格中统一命名。

## 8. 审稿最终意见

本项目已经从“页面和演示数据复现”进入“可运行的单机工程复现”：核心运行状态有版本、事务边界、Trace、审计和持久化结构，错误和坏数据路径也有自动化门禁。本轮修复的重点不是提高表面通过率，而是把历史数据、当前证据和实验 identity 分开，避免把兼容迁移和实验观察伪装成当前生产事实。

但是，当前结果仍不足以支持“原系统已完整复现”或“论文级已闭环”。论文必须明确研究对象是基于公开/现有材料重构的本地工程，必须把历史 37/59 统计降级为历史背景，把当前 74 条 Maven 测试和 20 条契约实验作为新的实现/实验事实，并保留模型—本体绑定、Replay、远程 Provider、权限、HA、性能与业务收益等边界。只要按补充章节的证据口径写作，当前结论是可审计、可复现且不过度声称的。
