# 固定映射基线与 Flexible Engine 对比实验协议

## 目的

本协议用于回答一个有限、可复核的问题：在相同输入、相同模型案例和相同初始种子下，仓库内的固定字段实现与当前 Flexible Engine 是否产生可解释的状态、错误、Trace、图谱、版本迁移和耗时差异。

本协议不声称复现原生产系统的黑盒行为，不使用线上服务、生产数据库或外部业务指标。

## 对照对象

| 对象 | 实现 | 允许的解释 |
|---|---|---|
| 固定映射基线 | `engine-admin-api/src/main/java/cn/finalartical/reproduction/admin/RigidMappingBaseline.java` | 预先声明的 questionnaire/interview-session 固定字段和固定状态转移；不调用 Flexible Engine、ontology 配置或 Provider |
| 当前引擎 | `EngineRuntimeService.execute` + `FlexibleEngine` + 配置的 Schema/Workflow/Ontology/Provider | 当前重构工程的真实运行路径 |

两侧由 `EngineRuntimeService.executeComparison` 生成独立 Run。每个配对必须满足：

1. `modelId`、事件、输入对象和 ontology input 的 `input_sha256` 相同；
2. `executionMode` 分别为 `RIGID_MAPPING_BASELINE` 和 `FLEXIBLE_ENGINE`；
3. `configuration_sha256` 彼此不同且在重复试验内稳定；
4. `comparisonId` 相同，`pairedRunId` 互相指向；
5. 两侧分别有自己的 Context、Snapshot、Trace 和持久化 Run。

## 案例与变量

| 案例 | 操作变量 | 预期可观察结果 |
|---|---|---|
| `questionnaire-basic` | 固定字段 `name`、`subjectId`，事件 `publish` | 两侧均可通过；比较调用链和本地耗时开销 |
| `questionnaire-dynamic-field` | 在 Schema 中新增 `reviewerNote`，输入携带该字段 | 固定基线拒绝未声明字段；Flexible Engine 按当前 Schema 承接 |
| `questionnaire-knowledge-graph` | 在 Schema 中增加 `subjects`，输入包含 subject/options | 两侧生成可比较的运行结果；柔性侧由真实 Provider 生成 ontology graph |

每个案例执行 12 次。每次使用新的临时 SQLite 文件，并从同一 `DefaultEngineSeed` 开始配置案例。耗时使用 `duration_ns`，p50 和 p95 只对本机本地运行的原始观测做描述统计。

## E 阶段：演化能力矩阵

E 阶段不把“更快”作为柔性引擎的默认收益，而是改变 Schema 配置后，用同一输入比较固定映射基线能否继续承接请求。三个案例各执行 12 次，每次使用全新 SQLite：

| 案例 | 配置变化 | 预期观察 |
|---|---|---|
| `interview-dynamic-field` | 为面试会话新增 `panelId` 字段 | 固定基线因未声明字段失败，Flexible Engine 按新 Schema 通过 |
| `interview-field-rename` | 将 `candidateName` 显式迁移为 `applicantName` | 固定基线仍要求旧字段而失败，Flexible Engine 使用 Schema v3 和迁移记录通过 |
| `questionnaire-dynamic-graph` | 新增 `subjects(JSON)` 并提交 subject/options | 两侧均通过；柔性侧保留真实运行图谱和提交证据 |

E 的主要指标为 `comparable_pairs`、`baseline_passed`、`flexible_passed`、`outcome_improved_pairs`、`adaptation_gain_rate` 和 `evidence_complete_pairs`。其中“适应性增益”定义为同一配对中 baseline 为 `FAILED` 且 flexible 为 `PASSED`，不等同于性能、兼容率或业务收益。E 还检查输入 hash 一致、配置 hash 区分、Trace 为 `COMMITTED`、Snapshot 成对存在以及 Run 配对关系完整。

## 产物

实验程序将以下内容写入输出目录：

- `D/result.json`：固定基线成对协议、案例摘要和全部 observations；
- `D/<case>-observations.json`：逐次配对的输入哈希、配置哈希、状态、错误码、Run ID 和耗时；
- `D/duration-comparison.svg`：从 JSON 摘要生成的可视化图，不包含人工填写的指标；
- `E/result.json`：演化能力矩阵、通过率、适应性增益和证据完整性；
- `E/<case>-observations.json`：逐次配对的 Schema 操作、迁移数量、状态、错误码、Trace 生命周期、证据门禁和耗时；
- `E/capability-comparison.svg`：从 E JSON 摘要生成的通过次数与适应性增益图；
- `summary.csv`：可供表格或论文制图复核的摘要行；
- `manifest.json`：源码修订、JDK、系统、输入文件和重建命令。

当前最终产物位于 `docs/实验证据/20260903_evolution_capability_final/`。论文数字必须以该目录同一实现修订下的 `report.json`、`D/result.json` 和 `E/result.json` 为准；`20260903_baseline_flexible_final/` 保留为上一阶段 D 的已提交证据，早期 v1/v2 产物仅作为缺陷发现过程材料。

## 结论边界

- 动态字段案例的“基线失败而 Flexible Engine 通过”可以写成当前固定基线下的工程观察。
- E 阶段若出现 baseline `12/36`、Flexible Engine `36/36` 且 24 对 outcome improved，只能写成当前固定基线下的演化适应性观察；字段新增和字段重命名不能被包装成通用兼容率。
- 基础案例和知识图谱案例中柔性侧耗时更高，说明柔性机制存在本地执行开销；不能把柔性自动写成更快。
- 12 次/案例不足以支持通用性能结论、统计显著性或生产容量结论；E 的 36 对也不改变这一限制。
- 没有原生产系统同版本输入/输出/错误样本时，不能写兼容率、黑盒等价、线上收益或业务提升。
- 系统展示结构化 Decision Evidence、Trace 和调用链，不记录或伪造不可验证的模型内部 COT。
