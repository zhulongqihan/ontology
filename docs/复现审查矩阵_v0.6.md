# 柔性引擎复现审查矩阵 v0.6

审查日期：2026-09-02
审查视角：论文审稿、复现工程、系统架构、证据检查
当前源码基线：以 Git 提交时的 `HEAD` 为准；实验报告记录实际运行时的 `source_revision`。

## 1. 审稿结论

当前工程可以支持“单机、本地、可重复、带边界声明的重构实现”这一结论，不能支持“原生产系统等价复现”“线上兼容率”“远程部署能力”或“业务收益”这些更强结论。

在本轮修改前，审查不通过的根因是：模型到本体的关系由同名规则隐式推导，Trace 在真实持久化提交前就可能被读成成功，source/target 基数只验证了一侧，实验只有契约回放而没有机制对照、故障注入和重复性。当前版本已对这些根因补齐代码、测试和论文口径。

## 4. 仍不能写进论文的主张

- 不能写“复现了原生产系统全部行为”或“20 条契约通过率等于线上兼容率”；当前契约 basis 是 `RECONSTRUCTED_BEHAVIOR`。
- 不能写“response 已成功送达客户端”；当前 Trace 只到调用方观察边界。
- 不能写“支持远程 Provider、RPC、权限审计、分布式高可用、容量基线或业务收益”；代码和原件均不足。
- 不能把旧 schema 4 SQLite、旧 JSON 或历史 37/59 条测试数字混入当前 79 条测试和 60 条契约断言。
- 不能把名称推导 comparator 说成完整 baseline；它只用于证明“同名假设”在跨标识场景下会失败。

## 5. 推荐审稿判定

若按工程复现论文审查：**有条件通过，要求补充原系统同版本黑盒对照后再声称兼容性**。当前版本的强项是证据边界诚实、关键状态有持久化来源、失败/幂等/并发有可执行验证；主要不足是缺少原系统对照、真实网络交付、远程 Provider、权限和性能证据。因此，本工程适合作为“可复核的重构方法与验证框架”提交，不适合作为“原系统等价实现”提交。
