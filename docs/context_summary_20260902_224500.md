## 已确认的关键实现风险

- `SqliteEngineStateRepository.write()` 在实际 SQL `COMMIT` 之前调用 `TraceLifecycle.markPersistenceCommitted(state)`，因此“提交后才标记 COMMITTED”的论文表述与调用时序不一致。
- SQLite 连接只设置 `PRAGMA foreign_keys = ON`，尚未发现 `busy_timeout`、统一锁等待策略或跨进程重试；现有并发测试主要是同一 JVM 内的两个 repository/service 实例。
- `ReproductionExperimentSuite` 的 B/C 主要使用 `JsonEngineStateRepository`；B 的失败注入发生在委托保存之前，不能证明 SQLite 中途故障时的原子性。C 统计的是内存 service 中的 Run 数，而非重启后从持久化介质核对的 Run 数。
- C 的三个 seed 只是写入报告的标签，固定 fixture 和执行顺序没有因 seed 改变，不能被表述为真正的随机重复实验。
- A 的名称基线是一个故意简化的字符串比较，不是完整的竞争实现；C 的 ablation 只是报告字符串，不是实际运行的去绑定系统。
- `EngineModel` 有 `ontologyTypeId`，但 `OntologyTypeConfig` 未见独立 ontology version；SQLite schema 009 也没有对该字段建立外键，需继续核对悬空绑定拒绝边界。
- 前端 `api.ts` 尚未自动读取 ETag 或发送 If-Match；需要通过真实浏览器和 HTTP 交互核对当前 UI 是否覆盖条件写入、加载、错误和空状态。
- 论文原稿仍包含待填写的作者/导师等元数据占位符；工程内旧审稿报告和补充材料仍可能保留 73/74 测试数或旧能力判断，存在跨文档矛盾。
